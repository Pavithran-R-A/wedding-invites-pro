# Feature readiness matrix

This is the anti-delusion document. Its purpose is to stop a future contributor (human or agent)
from reading a table name, a UI label or an unused component and concluding that a capability
exists.

**Definitions**

| Status | Meaning |
| --- | --- |
| `IMPLEMENTED` | Works in this build **and was actually exercised here**. A user can do the thing today. |
| `FOUNDATION` | Real code or schema exists that the feature will be built on, but the user-visible capability is incomplete or placeholder. **Not shippable as a claim.** This also covers code that is complete in source yet depends on an external environment (a configured Supabase project, email delivery) that this stage never verified. |
| `PLANNED V1` | Designed in these documents. No meaningful implementation. |
| `LATER` | Deliberately after V1. |
| `EXCLUDED` | We have decided not to build this. Reintroducing it needs a scope change, not a feature PR. |

on top of the Stage 5 pack-driven-authoring audit

on top of the Stage 4 tradition-pack audit

on top of the Stage 3 public-invitation audit
([`../audits/stage-3-public-invitation.md`](../audits/stage-3-public-invitation.md)) **and its §9
closure-repair and §10 final-truth-sync sections**, on top of the
Stage 2 domain and database audit
([`../audits/stage-2-domain-database.md`](../audits/stage-2-domain-database.md)) that replaced the
scaffold tables with the canonical domain. Product code reaches the database through **six** modules
in `src/integrations/supabase/`: `weddings.ts` reads and writes `weddings`, `design_templates`,
`invitation_drafts` and `invitation_versions`; `weddingContent.ts` reads and writes `wedding_people`,
`venues` and `wedding_events`; `traditionReleases.ts` reads `tradition_packs` and
`tradition_pack_releases` and writes one column of `weddings` (`tradition_pack_release_id`);
`weddingAssets.ts` reads and writes `wedding_assets` and is the only module that touches Storage,
where it sends bytes to a key the database minted and reads that key back from the row rather than
building one; `publication.ts` calls seven of the eight `api` wrapper functions and names
no table at all; `publicInvitation.ts` is the guest's single argument-free RPC — the eighth wrapper —
and names no table.
Between them that is **ten** canonical tables touched directly, plus the publication boundary
(`publications` and `private.access_tokens`) reached only through those functions. `product:check`'s
`canonical-table-read-outside-the-adapter` rule refuses a canonical-table `.from()` anywhere in `src/`
outside `src/integrations/supabase/`. The scaffold tables it used to name
(`projects`, `templates`, `guests`, `orders`, `payments`, `printers`) are archived in the `legacy`
schema, which no API role — `service_role` included — can reach. Canonical tables that **no product
code reads or writes yet** still exist (`guest_households`, `rsvp_responses`, `approval_requests`,
`approval_feedback`, `household_event_scopes`, `entitlements`, `user_roles`, …);
reading rule 1 applies to every one of them. `tradition_packs` was on that list when Stage 3 closed
and came off it in Stage 4, which also added `tradition_pack_releases` — a table that was never
unread, because it did not exist yet. **Stage 5 reached no new table from the client and added no
table at all.** Its one column is `tradition_pack_releases.review_packet_hash`, which no client selects
and no browser writes, and its new function surface is `internal_api`'s eleven maintenance verbs, which
`supabase/tests/api/stage3_publication.test.mjs:1152` (the case that carries the `API35` id in Stage 5's
addition — see the duplicate-id note in the Stage 5 audit's truth-sync section) measured as HTTP-**404**
(`PGRST202`) for every
credential shape rather than as a permission error — PostgREST never resolves the name in the exposed
profile, so a browser does not even learn whether the function exists. **Stage 6 took
`wedding_assets` off that list**, which is the first time this branch put a client `.from()` on a
table whose rows point at bytes; the row above is why that sentence describes code and not a
capability a host has been shown to have.

**What "verified" means here, because it changed in Stage 3.** Stages 0–2 never ran a Supabase
instance, so anything needing one was `FOUNDATION` by definition. Stage 3 runs against a **real local
stack** — Kong, GoTrue, PostgreSQL 17.6 and PostgREST on the platform images — with real JWTs, real
RLS and real HTTP, driven from a browser and from `@supabase/supabase-js`. PostgREST answers
`server: postgrest/16.3` on the final run of this branch (§9.12); `postgrest/16.2` was what the same
host and port reported earlier in the stage, and both readings are in the audit. No assertion in any
suite depends on either number. So a row below may now say
"exercised against the verified local stack": that is what closes Stage 2's declared gap. **Nothing is
deployed and no hosted project was touched**, so no row may claim a hosted customer can do anything
today, and reading rule 5 still refuses a row that says both at once.

**Stage 4 did not change that meaning; it widened what the same stack is asked.** The
`localvivaahvarnam` containers Stage 3 qualified are still the only backend this branch talks to, and
the release lifecycle, a host's pack selection, freeze-time wording resolution and the guest's
document were exercised against them — over HTTP with real JWTs, and against the **production bundle**
served by `vite preview` on `127.0.0.1:4173`. Two ceilings follow from that and are stated on every
Stage 4 row below: nothing is deployed, so no row claims a hosted customer can do anything; and no
release in that catalogue is customer content, so no row may claim reviewed wording exists.

**Stage 5 did not change that meaning either; it moved the authoring and review path from hand-written
SQL into a tool, and re-ran the same instrument.** The same `localvivaahvarnam` containers are still the
only backend, but at the §34 gate run the database was **reset from zero** — all 19 migrations applied in
filename order, `Finished supabase db reset on branch stage5/pack-driven-authoring-review` — and the live
schema, not only the migration files, is what the final numbers describe
([`../audits/stage-5-pack-driven-authoring-review.md`](../audits/stage-5-pack-driven-authoring-review.md)
§33.6). Everything a host or a guest can see was exercised against the **production bundle** on
`127.0.0.1:4173`, driven by clicking and typing (`scripts/stage5-ui-journeys.mjs`,
`scripts/stage5-a11y-mobile.mjs`, `scripts/stage5-network-privacy.mjs`). Three ceilings travel with every
Stage 5 row below, and none of them is a formality:

* **Nothing is deployed.** No hosted Supabase project was contacted, so no row may claim a hosted
  customer can do anything.
* **Every `reviewed` and `approved` release this stage exercised is a synthetic `TEST ONLY` fixture.**
  Those synthetic reviewed fixtures are **qualification data, not cultural authority**. Measured at the
  §35 review: 11 packs and 17 releases in the local catalogue, every one labelled `TEST ONLY`, every one
  `machine_assisted = true`, every one with `reviewed_by IS NULL`, and no release whose review basis
  claims a human reader with cultural authority. The tooling can therefore prove that a review *record*
  is bound to the bytes it reviewed; it cannot prove that anyone qualified reviewed the wording.
* **The real Tamil-and-English candidate is still a draft**, machine-assisted, not human-reviewed and not
  customer-selectable, and this stage did not approve, review or select it.

So a row below may now say "a maintenance operator moved a release through the lifecycle with the CLI
against the local stack", and a row may say "the host's editor showed the server's own blocking verdict".
No row may say "a reviewed pack exists", "a reviewer approved Tamil wording", or "this is in production".

**Stage 6 added a second store to talk about, and finished qualifying none of it.** The Storage
contract — a private `wedding-assets` bucket, a key the database mints, three `storage.objects`
policies with no UPDATE policy, and the `staged` → `ready` → `tombstoned` guards — is migration code
plus one adapter and one host panel, and `supabase/tests/api/stage6_storage.test.mjs` measured it
**33/33** over HTTP against the applied migration. What the stage did *not* get to do is re-run that
alongside the other four HTTP files, the six SQL batteries and any browser journey at the state that
carries the panel: the local Docker engine on this host stopped answering partway through the stage,
and the recovery attempts and the exact blocked set are recorded in
[`../audits/stage-6-storage-assets.md`](../audits/stage-6-storage-assets.md) §18. Two consequences
bind every row below:

* **No row may say a host can upload a file.** The wording is "the upload path exists in source and
  its battery measured 33/33 once"; the capability itself is `FOUNDATION`, which is what that label's
  own definition is for.
* **Nothing about a guest changed.** §7 of the same audit rules guest-facing asset delivery out of the
  stage, the Stage 3 publication battery still asserts the snapshot carries no `object_key`, and no
  policy was widened to accommodate an uploaded file. A row that says an invitation can show a family
  photograph would be false twice over — it is not built, and building it would need a threat model
  this document does not have.

## Reading rules

1. A table existing in `supabase/migrations/` does **not** make a feature `FOUNDATION` if nothing
   reads or writes it — say so, and keep it `PLANNED V1`.
2. A UI element that performs no persistence is `FOUNDATION` at best and must be labelled in-product
   as unavailable, not demo-able as working.
3. Moving a row from `PLANNED V1` to `IMPLEMENTED` requires: working code, a test or verified manual
   check, and an update to this matrix in the same change.
4. If this matrix and the UI ever disagree, the UI is wrong until proven otherwise.
5. `IMPLEMENTED` requires that the capability was **actually exercised in this build**. Code whose
   proof depends on an external environment we have not verified — a configured Supabase project,
   working email delivery, a live payment provider — stays `FOUNDATION` no matter how complete the
   source looks, and the note must name the missing verification. A row may never claim "a user can
   do this today" in the same breath as "not exercised against a live project".
